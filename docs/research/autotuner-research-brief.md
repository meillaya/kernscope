## 1. Triton Autotuner — verified in source

**Core design** ([`python/triton/runtime/autotuner.py`](https://github.com/triton-lang/triton/blob/4fa6ce6f86d398cc8e582f869d22096e481ca85c/python/triton/runtime/autotuner.py#L19-L125), official docs: [triton.autotune](https://triton-lang.org/main/python-api/generated/triton.autotune.html)):

- **`Config`** ([L328–L406](https://github.com/triton-lang/triton/blob/4fa6ce6f86d398cc8e582f869d22096e481ca85c/python/triton/runtime/autotuner.py#L328-L406)): free-form `kwargs` dict (your tile sizes, unroll, etc.) + first-class launch knobs `num_warps=4`, `num_stages=3`, `num_ctas=1` (SM90 clusters), `maxnreg` (register cap → PTX `.maxnreg`), optional per-config `pre_hook`, `ir_override`. Hashable/equality-comparable so configs can key dicts.
- **`key` re-tuning trigger** ([`run()`, L217–L282](https://github.com/triton-lang/triton/blob/4fa6ce6f86d398cc8e582f869d22096e481ca85c/python/triton/runtime/autotuner.py#L217-L282)): the cache key is the tuple of user-named args (`key=['M','N','K']`) **plus the `dtype` of every tensor argument** (L224–L226). In-memory `dict[tuple → Config]`; first call per key benchmarks, later calls replay the winner.
- **Pruning hooks** ([`prune_configs()`, L284–L313](https://github.com/triton-lang/triton/blob/4fa6ce6f86d398cc8e582f869d22096e481ca85c/python/triton/runtime/autotuner.py#L284-L313)): three-stage — (1) `early_config_prune(configs, named_args, **kwargs)` for legality filtering (must return ≥1 config); (2) optional `perf_model(**nargs, **config)` predicting runtime; (3) `top_k` (int or ≤1.0 fraction) keeps only the predicted-best before any real benchmarking. This is exactly the "cheap model → expensive measurement" funnel you want.
- **Timing** ([`_bench`, L133–L173](https://github.com/triton-lang/triton/blob/4fa6ce6f86d398cc8e582f869d22096e481ca85c/python/triton/runtime/autotuner.py#L133-L173)): each config is measured via `do_bench(kernel_call, quantiles=(0.5, 0.2, 0.8))`; **selection is `min` over the quantile tuples** (L243), i.e. **median-first**, with p20/p80 as tie-breakers. `OutOfResources` / `CompileTimeAssertionFailure` / `PTXASError` → `[inf, inf, inf]`, so infeasible configs lose gracefully instead of crashing the search (L168–L173).
- **`do_bench` protocol** ([`python/triton/testing.py` L288–L358](https://github.com/triton-lang/triton/blob/4fa6ce6f86d398cc8e582f869d22096e481ca85c/python/triton/testing.py#L288-L358)): warmup/rep are **time budgets, not iteration counts** (`warmup=25` ms, `rep=100` ms defaults). It (1) runs fn once + sync, (2) estimates per-call cost over 5 L2-flushed runs, (3) derives `n_warmup = warmup/estimate`, `n_repeat = rep/estimate`, (4) times **each rep individually with a CUDA-event pair**, flushing L2 before every rep (L342–L354), (5) summarizes via mean/median/min/max/quantiles ([`_summarize_statistics`, L66–L80](https://github.com/triton-lang/triton/blob/4fa6ce6f86d398cc8e582f869d22096e481ca85c/python/triton/testing.py#L66-L80)). A CUDA-graph variant exists ([`do_bench_cudagraph`, L140–L207](https://github.com/triton-lang/triton/blob/4fa6ce6f86d398cc8e582f869d22096e481ca85c/python/triton/testing.py#L140-L207)).
- **L2 flush implementation** ([`third_party/nvidia/backend/driver.py` L393–L407](https://github.com/triton-lang/triton/blob/4fa6ce6f86d398cc8e582f869d22096e481ca85c/third_party/nvidia/backend/driver.py#L393-L407)): a **256 MB device buffer zeroed (`cache.zero_()`) before each rep** — "to make sure that the L2 cache doesn't contain any input data". The default benchmarker is wired per-backend via `get_benchmarker()` (returns `triton.testing.do_bench`).
- **Disk caching of autotune results** ([`check_disk_cache`, L175–L215](https://github.com/triton-lang/triton/blob/4fa6ce6f86d398cc8e582f869d22096e481ca85c/python/triton/runtime/autotuner.py#L175-L215)): opt-in (`cache_results=True` / `knobs.autotuning.cache`). Cache key = **SHA-256 over `triton_key()` + backend/target hash + kernel `cache_key` + cache-invalidating env vars + tuning key + stringified configs**; result stored as `<kernel>.autotune.json` containing `{"key": ..., "configs_timings": [(config_dict, timing), ...]}`. On hit it reconstructs timings and re-picks the min **without re-benchmarking**. This is a ready-made JSON schema pattern for your tool (§8).
- **Correctness hooks**: `reset_to_zero` / `restore_value` / `pre_hook` / `post_hook` exist because autotuning runs the kernel many times on the same buffers ([L41–L82](https://github.com/triton-lang/triton/blob/4fa6ce6f86d398cc8e582f869d22096e481ca85c/python/triton/runtime/autotuner.py#L41-L82), doc note in the decorator L427–L431). Your C++ tool must equivalent-reset outputs between candidate runs.
- **`heuristics` decorator** ([L478–L512](https://github.com/triton-lang/triton/blob/4fa6ce6f86d398cc8e582f869d22096e481ca85c/python/triton/runtime/autotuner.py#L478-L512)): value-computed-from-args as the cheap alternative to search (e.g. `BLOCK_SIZE = next_power_of_2(x_size)`).
- Real search-space example: the matmul tutorial enumerates ~20 configs over `BLOCK_SIZE_M/N/K`, `GROUP_SIZE_M`, `num_stages`, `num_warps` ([`python/tutorials/03-matrix-multiplication.py` L160–L185](https://github.com/triton-lang/triton/blob/4fa6ce6f86d398cc8e582f869d22096e481ca85c/python/tutorials/03-matrix-multiplication.py#L160-L185)).
- Deprecation note: `warmup`/`rep`/`use_cuda_graph` params on `autotune` are deprecated in favor of injectable `do_bench` ([L104–L125](https://github.com/triton-lang/triton/blob/4fa6ce6f86d398cc8e582f869d22096e481ca85c/python/triton/runtime/autotuner.py#L104-L125), refs PR #4496).

**Lessons for C++**: configs as hashable structs with a `map<tuple, Config>` keyed on (problem shape, dtype); legality-prune → model-prune → measure funnel; median-of-reps selection with per-rep events; treat launch failures as +∞ cost; persist `(config, timing)` JSON keyed by a hash that includes *compiler version + target*.

## 2. TVM: AutoScheduler (Ansor) & MetaSchedule

**Status check (verified)**: `src/auto_scheduler/` no longer exists in TVM `main` (2026); MetaSchedule lives at [`src/s_tir/meta_schedule/`](https://github.com/apache/tvm/tree/27c2e019d0ce6182158020c7534dda4a3ce981ae/src/s_tir/meta_schedule). Ansor is therefore cited via its paper + historical design.

**Ansor (paper)** — Zheng et al., *Ansor: Generating High-Performance Tensor Programs for Deep Learning*, OSDI 2020 ([USENIX page](https://www.usenix.org/conference/osdi20/presentation/zheng), [PDF](https://www.usenix.org/system/files/osdi20-zheng.pdf)). Verified claims from the paper:
- **Hierarchical search space**: high-level "sketches" (loop-structure templates) enumerated by derivation rules, low-level details (tile sizes, unroll) filled by **random sampling** rather than full enumeration — this is what makes the space tractable.
- **Exploration = sample + evolutionary fine-tuning guided by a learned cost model**, plus a **task scheduler** that dynamically prioritizes subgraphs by expected end-to-end gain (up to 3.8×/2.6×/1.7× over SOTA on Intel/ARM/V100).
- Implementation was ~12K lines of C++ core ("3K for the search policy, 9K for infrastructure") — a useful size reference for your tool.

**MetaSchedule (verified in current source)** — the surviving, redesigned tuner:
- **Search space = schedule traces**: the design space is represented as *traces* (replayable scheduling op sequences) generated by `SpaceGenerator`/`ScheduleRule`s ([`src/s_tir/meta_schedule/space_generator/`, `schedule_rule/`](https://github.com/apache/tvm/tree/27c2e019d0ce6182158020c7534dda4a3ce981ae/src/s_tir/meta_schedule/space_generator)).
- **Evolutionary search** ([`evolutionary_search.cc`, `EvolutionarySearchNode` L253–L382](https://github.com/apache/tvm/blob/27c2e019d0ce6182158020c7534dda4a3ce981ae/src/s_tir/meta_schedule/search_strategy/evolutionary_search.cc#L253-L382)): knobs `population_size`, `genetic_num_iters`, `genetic_mutate_prob`, `init_measured_ratio`/`init_min_unmeasured` (seed population mixes **previously measured** candidates with fresh random ones), `num_empty_iters_before_early_stop`. Pipeline: `PickBestFromDatabase` → [`SampleInitPopulation` (L522)](https://github.com/apache/tvm/blob/27c2e019d0ce6182158020c7534dda4a3ce981ae/src/s_tir/meta_schedule/search_strategy/evolutionary_search.cc#L522) → [`EvolveWithCostModel` (L562+)](https://github.com/apache/tvm/blob/27c2e019d0ce6182158020c7534dda4a3ce981ae/src/s_tir/meta_schedule/search_strategy/evolutionary_search.cc#L562) (mutators sampled by probability; candidates scored by the cost model) → ε-greedy pick → real measurement → results fed back to database + cost model.
- **Cost models**: XGBoost (default), MLP, random baseline ([`python/tvm/s_tir/meta_schedule/cost_model/`](https://github.com/apache/tvm/tree/27c2e019d0ce6182158020c7534dda4a3ce981ae/python/tvm/s_tir/meta_schedule/cost_model); features from [`per_store_feature.cc`](https://github.com/apache/tvm/blob/27c2e019d0ce6182158020c7534dda4a3ce981ae/src/s_tir/meta_schedule/feature_extractor/per_store_feature.cc)).
- **Task schedulers**: round-robin and gradient-based ([`task_scheduler/`](https://github.com/apache/tvm/tree/27c2e019d0ce6182158020c7534dda4a3ce981ae/src/s_tir/meta_schedule/task_scheduler)).
- **JSON database** ([`json_database.cc`, `JSONDatabaseNode` L73–L161](https://github.com/apache/tvm/blob/27c2e019d0ce6182158020c7534dda4a3ce981ae/src/s_tir/meta_schedule/database/json_database.cc#L73-L161)): workloads indexed by **module hash** (`CommitWorkload` appends JSON lines to a workload file; records stored separately; `GetTopK(workload, k)` retrieval). Official docs confirm two **newline-delimited JSON** files in `work_dir`, warm-start seeding on re-runs, and `module_equality="anchor-block"` for cross-model record reuse ([MetaSchedule tutorial](https://tvm.apache.org/docs/deep_dive/tensor_ir/tutorials/meta_schedule.html), [API ref](https://tvm.apache.org/docs/reference/api/python/meta_schedule.html)).

**Borrow for C++**: trace/decision-sequence representation (mutate one decision at a time instead of whole configs); measured-results recycling into the initial population; cost-model-gated evolution with a hard measurement budget; NDJSON records keyed by workload hash.

## 3. Halide auto-schedulers (Adams2019)

Verified in [`src/autoschedulers/adams2019/`](https://github.com/halide/Halide/tree/4b349d89786d286483737e29cf2d6ac80ef53289/src/autoschedulers/adams2019):

- **Parameters** ([`CostModel.h` L19–L56](https://github.com/halide/Halide/blob/4b349d89786d286483737e29cf2d6ac80ef53289/src/autoschedulers/adams2019/CostModel.h#L19-L56)): `parallelism=16`, **`beam_size=32`** ("Use 1 to get a greedy search instead"), `random_dropout=100`, `weights_path`, `memory_limit`.
- **Coarse-to-fine beam search** ([`AutoSchedule.cpp`](https://github.com/halide/Halide/blob/4b349d89786d286483737e29cf2d6ac80ef53289/src/autoschedulers/adams2019/AutoSchedule.cpp#L225-L442)): `optimal_schedule_pass` expands states decision-by-decision, keeping the best `beam_size` at each depth (L272–L304); **5 passes** with random dropout for diversity (`num_passes = (beam_size == 1) ? 1 : 5`, L441–L442; [`random_dropout` L132–L142](https://github.com/halide/Halide/blob/4b349d89786d286483737e29cf2d6ac80ef53289/src/autoschedulers/adams2019/AutoSchedule.cpp#L132-L142)); states within 1.2× of the best get "blessed" into the next beam (L363).
- **Cost model interface is batched** ([`CostModel.h` L61–L80](https://github.com/halide/Halide/blob/4b349d89786d286483737e29cf2d6ac80ef53289/src/autoschedulers/adams2019/CostModel.h#L61-L80)): `enqueue(...)` many schedules, then one `evaluate_costs()` — designed for batched NN/boosted inference. The default is a learned model ([`DefaultCostModel.cpp`](https://github.com/halide/Halide/blob/4b349d89786d286483737e29cf2d6ac80ef53289/src/autoschedulers/adams2019/DefaultCostModel.cpp)) trained offline on randomly-generated programs (paper: Adams et al., *Learning to Optimize Halide with Tree Search and Random Programs*, SIGGRAPH 2019; repo also ships `retrain_cost_model.cpp` and `cost_model_generator.cpp`).
- **No live benchmarking inside the scheduler** — Adams2019 scores purely with the cost model and returns the best-found schedule (verified: no measurement loop in `AutoSchedule.cpp`). Sibling schedulers for comparison: `mullapudi2016` (analytic), `li2018` (RL), `anderson2021` (beam search variant).

**Borrow for C++**: beam search over an ordered decision sequence is the cheapest viable search when a decent cost model exists; batched cost-model evaluation; dropout for exploration; but note its weakness — model-only selection can miss winners, which is why Triton/TVM still measure. Your hybrid: beam/evolutionary candidate generation + real benchmarking of the survivors.

### 4b. CuTe layouts & swizzling

## 5. C++ template kernel-generation patterns for GEMM (verified references)

- **Block → warp → instruction tiling hierarchy**: CUTLASS documents the exact nested loop structure (CTA tile → warp tile → MMA instruction) with rationale — concurrency at threadblock/warp/core levels, locality in SMEM/registers ([`efficient_gemm.md` L20–L107](https://github.com/NVIDIA/cutlass/blob/dcf215af68a2d08d305076c152a06f201728cd53/media/docs/cpp/efficient_gemm.md#L20-L107)); threadblock tile as `ThreadblockShape::{kM,kN,kK}` tunable per target (L81–L83); warp-level GEMM via `mma.sync`/`wmma` with the explicit goal "access to shared memory should be bank conflict free" (L86–L95).
- **Double buffering / multistage pipelining**: CUTLASS 2.x double-buffers at threadblock-SMEM and warp-register scopes ([`efficient_gemm.md` L131–L155](https://github.com/NVIDIA/cutlass/blob/dcf215af68a2d08d305076c152a06f201728cd53/media/docs/cpp/efficient_gemm.md#L131-L155)); SM90 uses TMA producer / MMA consumer warp groups with an async pipeline (L229). A complete readable cp.async multistage mainloop is in [`examples/cute/tutorial/sgemm_sm80.cu` L250–L300](https://github.com/NVIDIA/cutlass/blob/dcf215af68a2d08d305076c152a06f201728cd53/examples/cute/tutorial/sgemm_sm80.cu#L250-L300): `K_PIPE_MAX` stages, `cp_async_fence()` / `cp_async_wait<K_PIPE_MAX-2>()`, rotating `smem_pipe_write/read` — the pattern your `pipeline stages` knob should generate. (cp.async semantics: [PTX ISA `cp.async`](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html#data-movement-and-conversion-instructions-cp-async).)
- **Vectorized global loads (128-bit)**: CuTe expresses this as a copy atom — `Copy_Atom<UniversalCopy<uint128_t>, TA>` giving 128-bit per-thread copies ([`examples/cute/tutorial/sgemm_2.cu` L282–L288](https://github.com/NVIDIA/cutlass/blob/dcf215af68a2d08d305076c152a06f201728cd53/examples/cute/tutorial/sgemm_2.cu#L282-L288)); the CUDA-side equivalents are `float4`/`uint4` vector types ([CUDA C++ Best Practices Guide, memory throughput / coalescing](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html)). Your `vector width` knob = {1,2,4} elements × 32-bit ↔ 32/64/128-bit accesses.
- **Padding vs XOR swizzling for bank conflicts**: two verified approaches — (1) XOR swizzle `Swizzle<3,3,3>` composition on the SMEM layout (sgemm_sm80.cu L358, swizzle.hpp L41–L63, cited above); (2) padding is the classic alternative described in the [CUDA Programming Guide's shared-memory/bank-conflict sections](https://docs.nvidia.com/cuda/cuda-c-programming-guide/index.html) (shared memory is 32 banks, 4-byte stride; padding shifts rows to avoid conflicts at the cost of capacity/alignment). CUTLASS prefers swizzling because it wastes no SMEM and keeps 128-bit alignment — relevant since your `stages × tile` product is usually SMEM-bound. Threadblock **rasterization** (CTA launch order for L2 reuse) is another enumerated knob in CUTLASS ([`efficient_gemm.md` L157+](https://github.com/NVIDIA/cutlass/blob/dcf215af68a2d08d305076c152a06f201728cd53/media/docs/cpp/efficient_gemm.md#L157-L160)).

## 7. Roofline model

**Foundations (primary source)**: Williams, Waterman & Patterson, *Roofline: An Insightful Visual Performance Model for Floating-Point Programs and Multicore Architectures*, CACM 52(4):65–76, Apr 2009 — [DOI 10.1145/1498765.1498785](https://dl.acm.org/doi/10.1145/1498765.1498785), [author PDF (eScholarship)](https://escholarship.org/content/qt78h8v7mr/qt78h8v7mr.pdf), [Berkeley TR EECS-2008-134](https://www2.eecs.berkeley.edu/Pubs/TechRpts/2008/Archive/EECS-2008-134.pdf). Key definitions verified from the paper: **operational intensity** = ops per byte of DRAM traffic (bytes counted *after* cache filtering); attainable perf = min(peak FLOPS, intensity × peak BW); **ridge point** = intensity where the two roofs meet; ceilings refined per-cache-level.

**GPU adaptations**:
- Nsight Compute implements multi-level GPU roofline natively — "Roofline Charts" chapter ([Profiling Guide PDF v2023.2, Ch. 8](https://docs.nvidia.com/nsight-compute/2023.2/pdf/ProfilingGuide.pdf); current [online guide](https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html)).
- Microbenchmark-based GPU characterization (how to *measure* the peaks rather than trust datasheets): Wong et al., *Demystifying GPU Microarchitecture through Microbenchmarking*, ISPASS 2010 — [PDF](https://www.stuffedcow.net/files/gpuarch-ispass2010.pdf), [code](https://github.com/spthm/cudabmk), DOI 10.1109/ISPASS.2010.5452013.

**Arithmetic intensity for your kernels** (derivations; the intensity *definition* is from the roofline paper):
- **GEMM (M×K·K×N)**: FLOPs = 2MNK; minimum DRAM bytes = s·(MK + KN + MN) with s = bytes/elem (assuming each element read once — achievable with good tiling). Square N: AI ≈ N/(3s) → e.g. fp16 N=4096 gives ≈ 683 F/B, far past any ridge point (A100 ridge ≈ 312 TF/2.04 TB/s ≈ 153 F/B) → compute-bound, as expected.
- **Softmax / LayerNorm / reduction**: O(1) FLOPs/element (~5: max, sub, exp, sum, div for softmax) with ≥1 read + 1 write → AI ≈ 5/(2s) ≈ 0.6 F/B (fp32) — **deeply memory-bound**; the FlashAttention paper makes the same point ("most operations in Transformers are bottlenecked by memory accesses"). For these, your report should show % of peak *bandwidth*, not TFLOPS.
- **Attention (FlashAttention-lite)**: FLOPs = 4N²d per head (two N×N matmuls: S=QKᵀ and O=PV, each 2N²d); standard attention HBM traffic Θ(Nd + N²) vs FlashAttention Θ(N²d²/M) where M = SRAM size ([Dao et al., FlashAttention, NeurIPS 2022, Theorem 2](https://arxiv.org/abs/2205.14135); [paper PDF](https://proceedings.neurips.cc/paper_files/paper/2022/file/67d57c32e20fd0a7a302cb81d36e40d5-Paper-Conference.pdf)). So attention AI scales with block size / SRAM residency — the roofline point should be computed from *actual* HBM traffic of your tiled implementation, mirroring FlashAttention's IO analysis.
