AMD ORACLE USED (documented choice)
-----------------------------------
The plan's original AMD oracle was to link libLLVM and call
GCNSubtarget::computeOccupancy directly (brief §1.1 L56-59) or shell out to
llvm-calc-occupancy (brief §1.1 L60-64). BOTH are impossible on this
toolchain:
  * llvm-calc-occupancy is ABSENT from LLVM 21.1.8 (verified: `which
    llvm-calc-occupancy` in the devenv shell -> not found). Documented in
    occupancy.cpp + occupancy.h comments.
  * GCNSubtarget.h is NOT installed: the AMDGPU backend headers live in
    llvm/lib/Target/AMDGPU/ (not under the public include tree shipped in
    the nix store -- verified by find(1) over the LLVM dev output), and the
    nixpkgs LLVM also ships no AMDGPU <-> GCNSubtarget export surface, so
    the class cannot be downcast from TargetMachine.
  => The AMD oracle is the DOCUMENTED GCNSubtarget occupancy math: the
  ROCm/Triton occ.sh threshold table (brief §1.3 L113-116) for CDNA and
  LLVM's getNumWavesPerEUWithNumVGPRs formula (AMDGPUBaseInfo.cpp L1371-
  1380, quoted in rdna3-constants.md evidence (d)) for RDNA3, both of which
  are exactly the math GCNSubtarget::getOccupancyWithNumVGPRs uses. The
  libs/arch waves_per_simd_from_vgprs helper the engine calls is itself
  this formula (arch_test pins it); the sweep asserts the engine reproduces
  every documented wave count across the full VGPR range.

RISKS / DEVIATIONS
------------------
  * NVIDIA oracle model difference (documented, not hidden): the engine
    implements the CPG-guide register formula the task pins (which the two
    pinned goldens REQUIRE: 9 blocks -> 0.375); cuda_occupancy.h additionally
    floors warps per 16K-register sub-partition and yields 8 blocks for the
    same case. The 360-case oracle grid uses only cases where the models
    agree (verified by a pre-commit native probe); the single diverging case
    class is pinned and documented in NvidiaOracleSubpartitionDivergence.
  * GCNSubtarget oracle substituted as documented above (headers unavailable
    in the installed LLVM 21; llvm-calc-occupancy absent). The occ.sh table
    is the task-sanctioned fallback oracle.
  * AMD limiter-name mapping: the max-waves-per-SM cap is reported as
    "threads" (task contract has no "warps" value; the two limits coincide
    for warp-aligned blocks); ties report "registers" (register-first tie-
    break, matching the polykernel oracle convention).
  * gfx1101 2048-thread blocks report blocks_per_sm 0: the arch DB models
    max_warps_per_sm 16 in wave64-equivalent units (rdna3-constants.md), so
    the arch model caps at 32 wave32s/CU while 2048 threads need 64. This is
    libs/arch's accounting (todo 6, MUST NOT modify); the engine faithfully
    applies the constants and the test documents the corner.
  * No libLLVM link required (AMDGPU backend headers unavailable); the
    engine is self-contained on libs/arch constants.
